# legal-rag-hybrid-retrieval

一个中文法律文本的检索后端。BM25 和向量各召回一路，用 RRF 合一下，再用 Cross-Encoder 把前几条候选重排一遍；生成层接了个大模型，回答里每句话都标出依据来自哪一段。向量存 pgvector，服务是 FastAPI，查询结果丢 Redis 缓存。

说起来起因挺简单：我看过的 RAG 项目和教程里，检索这一层基本都是直接上一套向量检索就结束了，很少有人真的把关键词检索和向量检索放在同一份语料、同一批问题上比过。大家默认"向量能理解语义，所以一定比关键词强"，这个默认我一直不太信，于是想自己跑一遍看看差多少。

结果是：至少在法律文本上，真不是这么回事。BM25 单路的 Recall@1 比纯向量高了 4.4 个点，而且这个差距在 1000 条问句上是统计显著的（95% 置信区间 [+0.023, +0.066]）。下面表格里的数都是真跑出来的，`python evaluate.py` 一条命令能复现，不用光信我说的。

## 结果

3000 段语料，**1000 条问句**，嵌入用 `BAAI/bge-small-zh-v1.5`，重排用 `BAAI/bge-reranker-base`：

|              | Recall@1 | 95% CI          | Recall@5 | MRR   |
| ------------ | -------: | --------------- | -------: | ----: |
| BM25         |    0.897 | [0.878, 0.916]  |    0.981 | 0.937 |
| 向量          |    0.853 | [0.830, 0.874]  |    0.969 | 0.905 |
| 混合 RRF      |    0.902 | [0.884, 0.920]  |    0.984 | 0.939 |
| 混合 + 重排    |    0.940 | [0.925, 0.954]  |    0.991 | 0.963 |

置信区间是配对 bootstrap 重采样 2000 次算的（`scripts/bootstrap_compare.py`）。加这一列是被坑出来的，原因写在下面的坑第 ⑥ 条。

几个值得一说的点：

法律文本里 BM25 确实赢过纯向量，+4.4 个点且置信区间不跨 0，这个结论站得住。原因想想也合理 —— 法条编号、罪名、程序名这些东西要的是精确匹配，语义模型擅长泛化，在这儿等于把信号稀释了。

但**混合只比单用 BM25 高 0.5 个点，而且不显著**（区间 [-0.007, +0.017] 跨 0）。这点挺打脸的：在 BM25 的主场里，融合几乎没带来增量。融合真正的价值是兜住纯向量的短板 —— 它比纯向量高 4.9 个点，显著。

四步里涨得最实在的其实是重排，比融合再高 3.8 个点。这个我一开始判错了，150 条的时候看着只涨 0.6 个点，我据此写过"重排性价比一般"，扩到 1000 条才发现不是那么回事。详见坑第 ⑥ 条。

## 怎么跑起来

不装模型不装数据库也能先把链路跑通，用的是哈希兜底嵌入加 20 段示例语料，**这个模式下的指标没有参考价值**，只是验证代码没坏：

```bash
pip install -r requirements.txt
EMBED_BACKEND=hash DATA_MODULE=data python evaluate.py
```

要复现上面那张表，需要的东西比第一种模式多三样：

- **pgvector 数据库**（5432）：存 3000 段语料的 512 维向量，用 Docker 起
- **嵌入和重排模型**：本地能加载就行，可以现下，也可以像我这样提前下好放本地
- **Redis**（6379）：只有跑 HTTP 服务时才用得上，单纯跑评测其实可以不起

```bash
# 1. 起 pgvector（db，5432）和 Redis（redis，6379）
#    只跑评测的话，后面那个 redis 可以不加
docker compose up -d db redis

# 2. 装嵌入 + 重排模型依赖，会带上 torch，2GB 左右
pip install sentence-transformers

# 3. 告诉程序连哪个库、用哪份语料（Windows PowerShell）
#    EVAL_MAX 给 1000，条数少了指标不稳，原因见踩坑第 ⑥ 条
$env:DATABASE_URL = "postgresql://postgres:postgres@localhost:5432/rag"
$env:DATA_MODULE  = "data_law"
$env:EVAL_MAX     = "1000"
$env:RERANK_MODEL = "BAAI/bge-reranker-base"
python evaluate.py

# 4. 起 FastAPI 服务（8000）。要用到缓存就再把 Redis 指过去
$env:REDIS_URL = "redis://localhost:6379/0"
uvicorn main:app --reload --port 8000
```

macOS / Linux 把 `$env:XXX = "..."` 换成 `export XXX="..."` 就行。

第一次跑会把 3000 段全部编码写进 pgvector，之后库里有了就直接跳过，终端会打印一行 `[skip]`。换语料但条数正好撞上时，记得 `REUSE_INDEX=0` 强制重建，不然会拿旧向量出结果。这个复用只对 pgvector 生效，内存模式每次进程重启都得重算。

`init_db.sql` 挂在 `docker-entrypoint-initdb.d` 上，db 容器第一次起来会自动建表，不用手动执行。但要注意：换嵌入模型一定得同步改 `init_db.sql` 里的 `vector(512)`，维度对不上会直接报错。

调接口：

```bash
curl -X POST http://localhost:8000/retrieve \
  -H "Content-Type: application/json" \
  -d '{"query": "如果被告人不服判决，有什么权利？", "topk": 3, "use_rerank": true}'
```

```json
{
  "ok": true,
  "cached": false,
  "results": [{"id": 0, "score": 0.9981, "text": "根据《刑事诉讼法》第294条……"}],
  "latency_ms": 123.45,
  "rerank": true
}
```

浏览器打开 `http://localhost:8000` 有个能直接输问题的演示页。

全部 Docker 化是 `docker compose up --build`，但 api 镜像默认不含 torch，需要真嵌入时得 `docker compose build --build-arg WITH_TORCH=true api`，镜像会大不少。

## 数据是哪来的

语料来自 HuggingFace 上的 [Brench/chinese_law_data_rag_ft](https://huggingface.co/datasets/Brench/chinese_law_data_rag_ft)，28 万多条中文法律问答，我取了前 3000 条存成 `law_qa_zh_3000.json`，文件里的 `_meta` 字段写了来源和字段含义。想重新抓或者换数量：

```bash
python scripts/fetch_law_data.py              # 默认 3000 条
TARGET_ROWS=10000 python scripts/fetch_law_data.py
```

脚本走的是 datasets-server 的 HTTP 接口，不用装 datasets 也不用 git-lfs，比较省事。

单 gold 那版评测集我一条都没自己标。数据本身就是问答对，那就换个用法：**回答当作语料段落**，**问句当作 query**，这条问句对应的那个回答，它的段落 id 天然就是 gold。于是一分钱不花就有了 query-passage 对。

要说清楚的是：标注成本不是消失了，是数据集作者已经付过了，我只是把问答对换了个用法。好处是我不用干这活，坏处是指标上限取决于那份数据本身的质量，我没法逐条验证每个问答是不是真的对得上。

这么白拿自然有代价，两个局限绕不开：

一是每个 query 只有一个 gold。法律问题常常好几条法条都算答得上，只认一个的话，召回了另外一条也不给分，算出来的数偏保守。

二是问句和它自己的回答天生会共享一些词（毕竟讲的是同一件事），BM25 在这上面多少占了点便宜。主表里那个 0.897 里面，有一部分可能就是这个原因，不全是 BM25 真的更强。

第二条我自己一直不踏实，所以标了一批多 gold 数据去验证，结果在下一节。

## 标了 30 条多 gold，看看单 gold 有没有骗我

从评测集里随机抽 30 条问句，BM25、向量、混合三路各取前 5 名凑成候选池（每条约 7.7 个候选，三路都参与所以池子本身不偏向哪一路），我自己把"内容上也能回答这个问题"的段落全勾上——这事没法交给程序，等于自己给自己打分。30 条里有 21 条在原 gold 之外又勾了新的，平均每条 1.87 个 gold。标注结果就在 `annotation/sheet.md`，勾了哪些一条条都在。

先说一个看表前必须知道的坑：**多 gold 下的 Recall@1 不能直接跟单 gold 比**。Recall 的分母是 gold 数，标了 2 个 gold 之后 top-1 最多只能命中 1 个，召回率天然被压到 0.5，掉下来是分母的锅不是方法的锅。所以下面主看 **Hit@1**（第一名在不在 gold 集合里，除的是查询数）和 MRR，这俩跟 gold 有几个无关。

|              | 单 gold Hit@1 | 95% CI          | 多 gold Hit@1 | 95% CI          | 多 gold Recall@5 |
| ------------ | ------------: | --------------- | ------------: | --------------- | ---------------: |
| BM25         |         0.835 | [0.700, 0.967]  |         0.901 | [0.800, 1.000]  |            0.950 |
| 向量          |         0.868 | [0.733, 0.967]  |         0.902 | [0.767, 1.000]  |            0.833 |
| 混合 RRF      |         0.869 | [0.733, 0.967]  |         0.935 | [0.833, 1.000]  |            0.972 |
| 混合 + 重排    |         0.869 | [0.733, 0.967]  |         0.935 | [0.833, 1.000]  |            0.917 |

回到最开始想验证的那件事：**没有证据表明单 gold 夸大了 BM25。** 换个标注口径，BM25 对向量的 Hit@1 差距变了 +0.032，区间 [+0.000, +0.100]，勉强不显著。关键是方向——如果 BM25 真靠"问句和自己的回答共享词汇"占了便宜，那多 gold 下它的优势该缩水才对（别的段落也含相关词，它不再能独占第一名），实际是略微变大一点。这个怀疑在数据上没成立。

**但 30 条样本根本不够比方法，这也是我第三次栽在样本量上。** 这 30 条上单 gold 的 Hit@1 是 BM25 0.835 / 向量 0.868，BM25 反而落后，跟 1000 条上 +4.4 个点的结论正好相反，而且两个口径的 CI 都跨 0。所以这批标注能回答"口径有没有骗我"，回答不了"谁更强"。想收紧到 ±0.05 得标到 100 条往上。

**意外收获在覆盖率上。** 换成看 top-5 能覆盖多少个 gold（同一批 query、同一批 gold，口径内部是公平的），BM25 0.950 / 向量 0.833，差 11.7 个点，区间 [+0.006, +0.239] 显著。也就是说要求"多找几条相关的"时，BM25 的优势比只看第一名明显得多。这跟主表方向一致，算是给"法律文本上 BM25 不输向量"补了个独立证据——而且这次的证据来自我自己标的 gold，不是靠词汇重叠白捡的。

**还有个没敢下结论的观察**：重排在覆盖率上是掉的（混合 0.972 → 重排后 0.917），我猜是重排倾向于把同一法条的不同表述堆在前面，牺牲了多样性。但 -0.034 不显著，30 条上说不清。真要查得专门做多样性指标的实验，现在没做。

## 生成层：到这里才是完整的 RAG

`/retrieve` 只能把原文段落捞出来，用户还得自己读、自己拼。`/ask` 在上面接了一层大模型，把几段归纳成一段通顺的话，并且每句标出依据来自哪一段。

```bash
curl -X POST http://localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"query": "如果被告人不服判决，有什么权利？", "topk": 3}'
```

```json
{
  "query": "如果被告人不服判决，有什么权利？",
  "answer": "被告人或其近亲属如果不服判决，有权向上一级人民法院上诉 [1]。辩护人经被告人或者其近亲属同意，也可以提出上诉 [1]。",
  "citations": [0, 978],
  "refused": false,
  "model": "qwen3.5-plus-2026-02-15",
  "passages": [{"id": 0, "score": 0.9981, "text": "根据《刑事诉讼法》第294条……"}],
  "usage": {"prompt_tokens": 564, "completion_tokens": 54, "total_tokens": 618}
}
```

法律场景接生成有个绕不开的问题：**模型会编法条**。读完几段原文，它可能顺嘴给你造一个"根据《XX法》第XXX条"，编号是它自己想出来的，看着还特别像真的。所以提示词里有一半篇幅是在约束这件事：不许编造法条编号、罪名、机关名称、期限、金额，资料里没出现的具体数字一律不许写。

光靠提示词压不住，另外加了两道保险。

一道是引用溯源。要求每句话都标 `[编号]`，接口把编号解析回真实段落 id 放进 `citations`，前端能点回去核对 —— 标了引用之后，编出来的东西也更容易一眼看出来。模型偶尔会引用一个不存在的编号（给了 3 段它写 `[4]`），这种直接丢掉，不让它进引用列表，因为引用是要给人点回去看的，指向空段落比不显示更糟。

另一道是要求它敢拒答：资料里没有的就原样输出"检索到的内容里没有相关规定"，不许推测，也不许用常识补。实测拿化妆品的段落去问刑事上诉和劳动仲裁，两次都老老实实拒答了，没编。

没配 `MODEL_API_KEY` 的时候 `/ask` 不会报错，会退化成纯检索（`answer` 为 `null`，附一句说明）。跟这个项目其它地方一样，先把降级留好，别让环境卡住人。

## 留痕这一层

一开始这个项目连一行日志都没有。检索链路做得再漂亮，出了问题是复盘不了的：不知道用户问了什么、命中了哪几段、模型有没有拒答、慢在哪一步。法律问答尤其不该这样——同样一句话，今天和明天给出不同答案，没有记录就无从解释。

所以加了 `audit.py`，每次请求往 JSONL 追加一行：

```json
{"ts": "2026-10-26T01:13:19+00:00", "endpoint": "retrieve", "query": "如果被告人不服判决？",
 "topk": 3, "cached": false, "rerank": true, "hit_ids": [1, 3, 0], "top_score": 0.0323,
 "latency_ms": 7.23}
```

`/ask` 会多记 `cited_ids`（答案实际引用了哪几段）、`refused`、`model` 和两个 token 数。攒够一批之后 `/stats` 直接给汇总：调用量、缓存命中率、平均与 p95 延迟、拒答数、错误数、token 消耗。

选 JSONL 而不是数据库，是因为它 `tail`、`grep`、`jq` 都能直接读，不用为了看一眼刚才发生了什么先开个客户端。规模上去了再换列式存储。

**被拒的请求也记。** 这条是补的：最早只有进到路由函数的请求才会写日志，而空 query、参数越界这类在 pydantic 那一层就被拦下了，压根到不了。`_handle_validation_error` 里补记一笔之后，日志里能看到 `endpoint: rejected` 的条目——有人在反复试探参数边界、某个调用方的字段格式总是不对，这些信号光看成功日志是发现不了的。

写盘这块有三个处理：加锁串行（uvicorn 跑线程池，多线程追加同一个文件容易写出半行）、坏行跳过（进程被强杀会留半行 JSON，读的时候跳过而不是让 `/stats` 崩掉）、写失败安静返回 `False` 并往 stderr 说一句——日志是旁路，它挂了不该让检索跟着挂。

## 输入这块不能敞着口

接口层原本是直接把 `req.query` 往下传的，没有任何约束。这意味着几十万字的问题照样会进到嵌入模型里，把它拖死甚至撑爆；`topk` 传个负数会静默切片出错，还不报错。现在入口挡住了：

| 输入 | 约束 | 超了怎么办 |
| --- | --- | --- |
| `query` | 过滤首尾空白后非空，≤ 1000 字 | 422 + `invalid_query` |
| `topk` | 1 ~ 20 的整数 | 422 + `invalid_request` |

顺带说一下为什么要 strip：不去掉首尾空白的话，「退货 」和「退货」会生成两个不同的缓存 key，同一句话被重复算一遍，缓存命中率也被稀释。

错误处理统一成一个结构，前端按 `code` 分支，不用去解析 message 文本：

```json
{"ok": false, "error": {"code": "invalid_query", "message": "query 不能为空"}}
```

三个码：`invalid_query` 是输入不合规，`invalid_request` 是字段类型或范围不对，`internal_error` 是没预料到的。最后一个会在服务端打完整堆栈——排查需要，但对外只给错误码，内部路径、SQL、模型地址这些不出去。

## 几个设计上的选择

**融合为什么用 RRF。** BM25 的分数是 TF-IDF 量纲，能到几十；向量相似度是 0~1。两边加起来之前得先归一化，而归一化系数对语料分布特别敏感，换批数据就得重调。RRF 只看名次，`score = Σ 1/(60 + rank)`，天生跨量纲，也不用调参。省事且稳。

顺带交代一下那个 60 是怎么来的：RRF 原始论文里的默认值，而那篇用的是英文数据集。我一开始直接抄了，后来补了组消融（`scripts/ablate_rrf_k.py`）：

| k        | Recall@1 | Recall@5 | MRR   |
| -------- | -------: | -------: | ----: |
| 1        |    0.900 |    0.987 | 0.938 |
| 5        |    0.907 |    0.987 | 0.943 |
| 10 ~ 200 |    0.907 |    0.987 | 0.942 |

结论是这东西对 k 极不敏感：5 到 200 之间三个指标基本不动，只有小到 1 的时候会掉到 0.900，因为名次权重太陡，等于退化成只看第一名。所以 60 谈不上最优（k=5 时 MRR 高 0.001），但也不算拍错 —— 差在千分位上，与其纠结这个，不如把心思花在召回侧。换个角度说，参数不敏感本身就是 RRF 相对加权求和的优势。

**重排放在第二阶段，纯粹是因为它太贵。** Cross-Encoder 要把 query 和 doc 拼一起完整过一遍 BERT，精度是高，但每条候选都要一次前向。3000 段全量重排就是 3000 次前向，延迟没法看。所以先用便宜的方式召回 10 条，再用贵的模型排这 10 条。召回和精排分开，做搜索的基本都这么拆，没什么新鲜的，但确实有效。

**缓存 key 里不只有 query。** 拼成 `rag:{query}:{topk}:{use_rerank}`。少任何一个字段，不同参数的检索结果就会互相串味。TTL 设的是 600 秒，知识库更新之后旧结果得尽快失效 —— 多算一次检索的成本，比返回过期法条低得多。

**降级留得到处都是。** 没配 `DATABASE_URL` 就用内存向量库，没配 `REDIS_URL` 就用 fakeredis，模型加载失败就回退哈希嵌入，没配 `MODEL_API_KEY` 就退回纯检索。好处是换台机器装上 requirements 就能跑，不会被环境卡住。坏处是会**静默降级出一版假指标**，所以 `evaluate.py` 每次都会打印当前用的是哪种嵌入后端，看到 `hash` 就别当真。

## 踩过的坑

**Windows 下 HF 缓存把 config.json 弄成 0 字节。** 报 `OSError: config file is not a valid JSON`，我一开始以为是网不好，重试好几遍。实际是符号链接：HF 用 symlink 把 `snapshots/` 指到 `blobs/`，Windows 没开开发者模式时创建失败，退化成空文件。解决办法是删掉坏缓存，然后 `HF_HUB_DISABLE_SYMLINKS=1` 重新下载（改成复制而非链接）。Windows 用户建议直接把这条写进环境变量。

**模型在本地却加载不出来。** 同上联网校验的问题，网络不通时报 502，代码 catch 住然后悄悄回退哈希嵌入 —— 指标看着挺正常，其实是假的。设 `HF_HUB_OFFLINE=1` 和 `TRANSFORMERS_OFFLINE=1` 走离线加载。

**psycopg3 写向量报类型错误。** Python list 不能直接丢给 `vector` 列。优先用 `pgvector.psycopg.register_vector`（能直接吃 numpy 数组），没装这个包就退化成拼 `'[v1,v2,...]'` 字符串再 `::vector` 强转，两条路都验过。

**指标天花板，这个是坑里最深的。** 语料 20 段的时候，四种方案 Recall 全是 1.000。扩到 600 段，还是普遍 0.98+，完全分不出高下。查下来是两个原因：语料太少，以及评测问句写得太像原文关键词，等于给两路都送分。最后把语料加到 3000 段、指标换成更难的 Recall@1、问句用真实自然语言，才拿到有区分度的数。**教训是：指标全满分时先怀疑天花板，别急着调模型。**

**换嵌入模型忘了改表。** `bge-small-zh-v1.5` 是 512 维，`init_db.sql` 里就得写 `vector(512)`。换 `bge-base-zh` 是 768 维，不改表直接报错。

**样本量不够，结论会整个反过来。** 这个坑我栽了三次，代价最大。

第一次：一开始用 150 条评测，跑出 BM25 0.900 / 向量 0.853，看着挺稳。后来为了做标注随机抽 30 条出来跑同一批方法，结果变成向量 0.885 > BM25 0.808，结论整个掉了个头。加了 bootstrap 才看清：150 条时 BM25 减向量的区间是 [+0.000, +0.093]，下界正好压在 0 上，属于勉强不显著。扩到 1000 条才收紧成 [+0.023, +0.066]，结论才算站住。

第二次更蠢：150 条时看混合 + 重排只比融合高 0.6 个点，我据此在 README 里写过"重排性价比一般"。扩到 1000 条再看，是 +3.8 个点而且显著 —— 四个方案里涨得最实在的一步就是它，我差点因为样本量把最有用的一环否掉。

第三次是标完多 gold 那批数据：30 条上跑出来 BM25 0.835 / 向量 0.868，BM25 反而落后，跟 1000 条上 +4.4 个点完全对不上。这次我没再急着改结论，因为已经知道 30 条是什么分量 —— 直接去看置信区间，两个口径都跨 0，说明这批评注只够回答"标注口径有没有影响"，不够回答"谁更强"。

所以现在默认跑 1000 条（`EVAL_MAX=1000`），150 条只用来快速冒烟。**教训：指标差几个点的时候，先看样本量和置信区间，再下结论。样本小的时候，正确做法不是换个结论，是承认这个样本给不出结论。**

**推理型模型默认会把思考过程一起吐出来。** 接生成层的时候第一次调用直接超时，我以为是网络问题，查下来不是：`qwen3.5-plus` 这类模型会先输出一大段 `reasoning_content` 再给答案。

实测同一个问题，一个 46 字的答案配了 4286 字的思考过程：

|              | 输出 token | 耗时    |
| ------------ | --------: | ------- |
| 开着思考模式  |     1434  | 28.5 秒 |
| 关掉          |       30  | 3.3 秒  |

**98% 的输出 token 和 89% 的时间都花在思考上**，而答案本身没什么区别 —— 因为这活儿是照着给定的资料归纳，不是推演。加上 `enable_thinking: false` 就好了，代码里默认关，`MODEL_ENABLE_THINKING=1` 可以打开。**教训：换模型后先看一眼 `usage` 里的 `reasoning_tokens`，数字很大说明它是推理型的，而且你正在为用不上的思考过程付费。**

## 环境变量

复制 `.env.example` 改成 `.env` 就行，全部都有降级默认值，一个不配也能跑。

| 变量                | 默认                     | 说明                                  |
| ------------------- | ------------------------ | ------------------------------------- |
| `DATABASE_URL`      | 空                       | 空则内存向量库，填了走真实 pgvector    |
| `REDIS_URL`         | 空                       | 空则 fakeredis，填了走真实 Redis       |
| `EMBED_BACKEND`     | `st`                     | `st` 真实句向量 / `hash` 离线兜底      |
| `EMBED_MODEL`       | `BAAI/bge-small-zh-v1.5` | 512 维，换模型要同步改表               |
| `RERANK_MODEL`      | 空                       | 空则跳过重排                           |
| `DATA_MODULE`       | `data`                   | `data_law` 法律语料 / `data` 示例语料  |
| `TOPK` / `EVAL_MAX` | `5` / `150`              | 返回条数 / 评测问句条数，正式跑建议 `EVAL_MAX=1000` |
| `REUSE_INDEX`       | `1`                      | 库里已有同样条数时跳过重建，换语料要设 `0` |
| `MODEL_API_BASE`    | DashScope 兼容模式        | 生成层接口，任何 OpenAI 兼容服务都行       |
| `MODEL_API_KEY`     | 空                       | 空则 `/ask` 退化成纯检索                   |
| `MODEL_NAME`        | `qwen-plus`              | 实测用的是 `qwen3.5-plus-2026-02-15`        |
| `MODEL_ENABLE_THINKING` | `0`                  | 推理型模型是否输出思考过程，默认关          |
| `MODEL_TIMEOUT`     | `120`                    | 生成超时秒数                               |
| `PASSAGE_MAX_CHARS` | `600`                    | 送进提示词的每段正文最长字数                |
| `AUDIT_ENABLED`     | `1`                      | 是否落审计日志，设 `0` 关掉                 |
| `AUDIT_LOG_PATH`    | 空                       | 留空则写在项目根目录 `audit.jsonl`         |
| `MAX_QUERY_CHARS`   | `1000`                   | query 长度上限，超了返回 422               |
| `MAX_TOPK`          | `20`                     | topk 上限，同时必须 ≥ 1                    |

配置除了环境变量，也支持写在 `.env` 里（`config.py` 自己解析，没引 python-dotenv）。两份都有的话**以环境变量为准**，方便临时换个模型试。注意 `.env` 在 `.gitignore` 里，key 不会跟着提交。

## 代码结构

```
config.py              配置，全走环境变量
embedding.py           嵌入层，含中文切分和 hash 兜底
vectorstore.py         pgvector / 内存，两种向量库
retrievers.py          BM25、向量、RRF 融合、重排
cache.py               Redis 查询缓存
main.py                FastAPI：/retrieve、/ask、/stats、/health、演示页
generator.py           生成层：提示词拼装、chat/completions 调用、引用解析
audit.py               审计：请求落 JSONL，/stats 汇总调用量、命中率、p95、拒答与错误
evaluate.py            四方案评测，输出 Recall@1/@5、MRR
data_law.py            法律语料与评测集构建
data.py                20 段示例语料
scripts/fetch_law_data.py   重新抓语料
scripts/ablate_rrf_k.py     RRF 的 k 值消融
scripts/bootstrap_compare.py    各方法的 bootstrap 置信区间与显著性检验
scripts/build_annotation_sheet.py   生成多 gold 标注表（把候选池捞出来供人工勾选）
scripts/eval_multi_gold.py     用标好的多 gold 数据重新评测，跟单 gold 对照（带 bootstrap）
annotation/sheet.md            30 条问句的人工标注结果，每行候选都留着
tests/test_reuse_index.py   索引复用的测试，mock 掉数据库，不用 Docker 也能跑
tests/test_generator.py     生成层测试，不联网不花钱
tests/test_audit_and_validation.py    审计日志与输入校验，覆盖 6 类畸形输入与内部异常降级
init_db.sql            建表语句
```

测试这么跑，不用装 pytest：

```bash
python tests/test_reuse_index.py
python tests/test_generator.py
python tests/test_audit_and_validation.py
```

## 还没做

- 标注量从 30 条扩到 100 条：现在多 gold 的置信区间太宽，只够定性。扩上去才能让"BM25 覆盖率更高"这个结论真正站住
- 检索多样性：重排后覆盖率下降是个没验证的猜测，得补专门的实验
- 文本切分：现在直接拿整段回答当检索单元，长文档得上 chunk + overlap
- 向量索引：HNSW 没开，语句在 `init_db.sql` 注释里。3000 段这规模全表扫描更快，开了反而慢
- 生成质量还没评：`/ask` 能出答案了，但答案对不对、引用标得准不准，现在没有任何量化。多 gold 那批标注可以用来做这件事（看答案覆盖了几个 gold），审计日志落下来之后也有素材了，下一步打算做
- 日志轮转：JSONL 会一直追加，长期跑要自己接 logrotate 或定期归档，没做
- 多租户：没做隔离
